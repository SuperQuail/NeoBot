# 流程图写作规范（所有图、所有作者必须遵守）

> 本文件是 \`docs/flow/\` 的唯一格式与粒度来源。写图前先读它，写完用
> \`scripts/flow/check_flow_diagrams.py\` 自检。目标读者是**维护者与后续 agent**：
> 拿着图就能定位到代码、能看懂分叉判据、能知道失败停在哪。

## 0. 一句话标准

**细节到「读图 ≈ 读代码逻辑」，但节点数仍然可评审**：主图只画主干，细节一律下沉到
\`## 细节\` 里的折叠块（每个折叠块都可以单独打开、单独截图）。
对照物：\`docs/flow/02b-willing-probability.md\`（把 0.5 起点、+0.15 问句加成、
八个乘数、六种短路全部写清楚的那种粒度）。

## 1. 文件与图头

一个文件一张图，文件名 \`NN-slug.md\`（两位序号 + 短横线 + 英文 slug）。

\`\`\`markdown
---
flow: 05-llm-routing
covers:
  - app/src/neobot_app/assembly/
  - packages/chat/src/neobot_chat/models.py
verified_against: dfe5416
verified_hash: PENDING
---

# 05 模型路由与降级：角色/编号路由 · 原生视觉降级 · 计费与统计
\`\`\`

* \`flow\` 必须等于文件名（去掉 \`.md\`），否则 F1 直接阻断。
* \`covers\` 是**漂移检测范围**：写目录或文件，必须真实存在，只对范围内的 \`*.py\` 内容哈希负责。
  宁可写窄写准（一个模块目录），不要写 \`app/\` 这种大而空的路径。
* \`verified_hash\` 不用手写：写完跑
  \`uv run python scripts/flow/check_flow_diagrams.py --update\` 由工具盖章。
* \`verified_against\` 写你核对时的提交短号（\`git rev-parse --short HEAD\`）。

## 2. 必需章节（顺序固定，F3 检查）

| 章节 | 内容要求 |
|---|---|
| \`## 范围\` | 这张图画什么、**不画什么**（指向相邻图），以及 spec 与现实的差异提示 |
| \`## 流程\` | 一张 mermaid \`flowchart\`：主干链路，含关键分叉判据；节点里写**符号名** |
| \`## 时序\` | 一张 mermaid \`sequenceDiagram\`：参与者是模块/类，标出「谁等谁」「哪一步不致命」 |
| \`## 细节\` | **若干折叠块**（见 §3）：细到每个判据、每个系数、每个阈值 |
| \`## 关键状态\` | 表格：状态 / 谁置位 / 谁清理 / **失败时停在哪** |
| \`## 易错点\` | 历史坑（引用 \`fix(N)\`）、反直觉设计、改动时的连带影响 |

## 3. 折叠细节块（本仓库的「按需展开」约定）

\`\`\`markdown
## 细节

<details>
### 小节标题：一句话说清这块讲什么

\`\`\`mermaid
flowchart TD
    A["入口 文件:行号"] --> B{"判据"}
\`\`\`

正文补充：阈值、默认值、行号、反例、为什么这么设计。
</details>
\`\`\`

约定：

* 每个折叠块 = 一个**可独立截图**的完整逻辑单元（建议 8–24 个节点）。
* 每张图 **5–14 个折叠块**；超过 14 个说明该拆图了（检查脚本会阻断）。
* 折叠块内的 \`###\` 标题会出现在页面折叠条上，写清「这块解决什么问题」。
* 默认折叠：主流程先看，细节按需展开 —— 不要把细节直接铺在正文里。

## 4. 节点与连线规范

* 节点文本用 \`"…"\` 包起来（含空格/标点/括号时必须包）。
* 节点标注**符号名优先**，行号只标「关键判断点」：例 \`"evaluate()｜builtin.py:15"\`。
* 节点里的换行用 \`<br/>\`；\`<details>\` 里不能出现裸 \`<>\` 之外的 HTML。
* 连线标签写**判据**而不是「是/否」光秃秃两个词：\`-- 队列满 -->\`、\`-- provider 异常 -->\`。
* 失败/降级路径用虚线：\`-.->\`。
* \`subgraph\` 用来分组（如「配置层 / 运行时层」），不要用来当节点。
* 主流程 ≤ 25 个节点、≤ 120 行；折叠块同样受此限制（检查脚本按块统计）。

## 5. 必须写进图里的东西

1. **判据**：每个菱形写清楚「拿什么字段/什么函数」判的。
2. **阈值与默认值**：超时、上限、系数、窗口大小，写具体数字并标注配置项名。
3. **失败语义**：抛异常、降级、丢弃、重试 —— 四种要能区分开。
4. **状态归属**：谁置位、谁清理；终态无出边要写出来。
5. **观测点**：日志/reasons/统计字段名（排查问题时的第一手线索）。
6. **不做事的地方**：NO-OP、注释掉的代码、遗留实现 —— 明确写「别当有效链路」。

## 6. 语言与风格

* 全中文（除符号名、配置键、状态名）。
* 表格优先于长段落；正文里代码引用用反引号。
* 不写「可能/大概」：不确定就去读代码，确认不了就写「未确认，见 文件:行号」。

## 7. 自检流程（每个作者都要走）

\`\`\`powershell
uv run python scripts/flow/check_flow_diagrams.py --update   # 盖章 + 自检（F1/F2/F3）
node scripts/flow/shoot_flow.mjs <你的图名> --url http://127.0.0.1:<端口>
\`\`\`

* 检查必须全绿（阻断 0 项）再提交；
* 截图落在 \`docs/flow/shots/<图名>.png\`，用于交付评审。

## 8. 反例（不要这么写）

* ❌ \`A[处理消息] --> B[回复]\` —— 没有符号名、没有判据、没有失败语义。
* ❌ 把 60 个节点塞进主流程 —— 该拆成主图 + 折叠块。
* ❌ 细节只写「见代码」 —— 图的价值就是省掉这一次跳转。
* ❌ \`covers: [app/]\` —— 漂移检测会变成「一动全红」，等于没有检测。
