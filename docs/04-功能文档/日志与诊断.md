# 日志与诊断

NeoBot 是单 Bot 进程。日志沿用 Loguru，终端展示使用 Rich；不引入多账号注册表或按 Bot 路由的日志实例。定位上下文围绕会话、回复事件、任务与插件组织。

## 输出与级别

| 出口 | 默认最低级别 | 用途 |
| --- | --- | --- |
| 控制台 stdout | INFO | 消息摘要、运行结果、需要处理的告警 |
| `data/logs/neobot.log` | DEBUG | 调试细节、组件阶段、工具调用与排障 |
| 网页面板实时日志 | INFO | 最近运行记录，可展开字段、调用位置和异常 |
| 自修复错误采集 | ERROR | 具备自修复资格的错误，继续排除上游瞬时故障和自修复自身日志 |

控制台时间显示为 `HH:mm:ss`，级别固定为四字符：`TRCE`、`DBUG`、`INFO`、`SUCC`、`WARN`、`ERRO`、`CRIT`。默认仅显示时间、级别和正文；在 `config.toml` 的 `[debug]` 中设置 `console_show_module = true` 并重启进程，可显示模块列。长正文在正文列换行。会话、任务、工具与耗时等精选上下文另起一行；路由事件名、完整路径和参数对象等诊断字段保留在文件与面板中，不逐行堆在控制台正文后。

基础插件与面板启动后，立即显示铺满终端宽度的「WebUI 已就绪」提示框和实际访问地址；OneBot 首次连接观察与其余 Bot 初始化继续进行，不再推迟地址提示。此时会明确显示「Bot 正在初始化」，不提前宣告 Bot 已启动。

终端自动探测颜色能力；容器和文件重定向输出同样的短时间与四字符级别，纯文本无 ANSI 颜色，不按终端宽度硬折行。所有常规日志仍走 stdout。文件按 10 MB 轮转、保留 7 天，保留完整时间精度、原始级别和全部结构化字段。面板保留近期内存记录，下载的是当前筛选结果，不是历史日志文件。

正文、字段和异常在分发前统一脱敏。日志异常在终端使用 Rich 彩色堆栈，展示完整调用链、文件、行号、函数、异常原因和因果链/异常分组。CLI 的主线程及工作线程未捕获异常也使用这一展示。Rich 只渲染已经脱敏的堆栈快照，不读取源码和局部变量；重定向输出仍为纯文本，文件与面板保留独立异常信息。密钥字段支持嵌套对象和常见命名形式。不要把完整凭据、请求体或用户消息对象当作调试字段。

## 结构化字段

业务层继续使用 `neobot_contracts.ports.logging.Logger`，无需依赖 Rich：

```python
logger = logger_factory.get_logger("app.reply").bind(chat_flow_id="group:123")
logger.info("回复已发出", event="reply.sent", event_id="r1", message_count=2)

try:
    await send_notification()
except Exception:
    logger.warning("通知发送失败", event="notification.failed", task_id="t1", exc_info=True)
```

- `message` 是可读的事实摘要；参数进入独立 `fields`，不再由适配器拼进正文。
- `bind()` 上下文与单次调用字段合并，同名字段以单次调用为准。
- 常用字段为 `event`、`event_id`、`chat_flow_id`、`task_id`、`plugin_name`；不要求 `bot_id`。
- `exc_info=True` 在异常处理块内捕获堆栈；`.exception()` 保留 ERROR 语义。
- 运行时 `kind="log"` 事件还携带时间戳、模块、文件、行号、函数和独立 `exception` 对象。stdlib logging 的 extra、stacklevel 和异常也保留。
- 结构化容器限制深度和元素数，过长字段有截断标记，不保留任意业务对象的引用。

API 调用统计使用成功写入 OneBot 连接后的 `onebot.api.sent` 事件，转换为独立 `kind="metric"` 信封；不再通过中文日志正文推断动作，也不因控制台或面板隐藏 DEBUG 而停止计数。不等待回执时，它表示请求已写入连接，不代表对端已执行成功。

## 记录原则与本轮治理

- INFO 记录实际状态或结果。主动取消、待机、成功操作和明确关闭的可选能力按正常状态处理；用户启用的能力发生降级仍可 WARNING。
- 每个事实由最接近结果的一层负责记录。消息接收、回复终态和通知交付保留摘要，转发、意愿判定、逐工具细节放 DEBUG。
- 回复送达后，模型正常 cancel 收尾不告警；送达后的真实异常仍保留原因与堆栈，不能因用户已经收到消息而隐藏后续失败。
- 持续故障记录首次发生、周期汇总与恢复。心跳告警和恢复成对；定时任务的相同轮询故障每 300 秒汇总抑制次数，状态表有界；表情扫描按批次汇总失败。
- 睡眠开始、到期和主动唤醒各记录状态变化，ticker 继续检查到期，不再每分钟播报剩余时间。
- 启动保留组件阶段到 DEBUG 文件，最终记录结果和耗时；启动未完成时不提前报告就绪。
- 嵌入式数据库迁移沿用宿主日志配置，Alembic 内部插件枚举与迁移步骤归 DEBUG，控制台只保留完成与耗时摘要；独立 Alembic 命令仍使用其 ini 配置。
- 当前装配不走的兼容分支和防御检查不会因“看起来没有日志输出”而删除。

这些改动逐步覆盖 #159–#165 的主要路径。#166 的不可达判断需逐项核对：公开的旧 adapter 群名模块、无 hub 兼容回退、备份内层文件存在检查等暂时保留，不能据此认定该 issue 已完成。

## 异步出口

应用异步启动时绑定主事件循环，工作线程也能向面板和自修复投递日志。两个异步出口各有最多 512 条待处理记录，顺序消费；满时丢弃新记录，不无限创建任务。接收器更换时丢弃上一代待处理记录，避免软重启后投递给旧实例。

消费者处理日志时产生的诊断不会再次进入同一个异步出口，控制台和文件仍会记录；这些反馈计入 dropped。每消费 64 条让出主循环，避免持续日志妨碍心跳和关闭超时。

关闭最终记录后最多等待 2 秒冲刷异步出口。超时不会取消正在处理的记录；文件输出仍为同步落盘。开发诊断可通过 `log_delivery_stats()` 查看各出口的 pending、dropped 和 failed 计数，`flush_log_sinks()` 返回是否在预算内完成。
