# 记忆系统

NeoBot 拥有多层记忆体系，从短期上下文到长期档案，让 Bot 能「记住」用户、群聊与共同经历。记忆服务位于 `packages/memory`，记忆相关配置位于 `agent.memory`。

## 记忆层级

| 层级 | 载体 | 说明 |
|---|---|---|
| 短期上下文 | 消息队列（[`message/queue.py`](../../app/src/neobot_app/message/queue.py)） | 当前聊天流内的消息，上限约 100 条 |
| 触发式记忆 | 记忆 Agent（`agent_model.memory`） | 按消息间隔自动触发，总结当前对话写入档案 |
| 档案记忆 | [`packages/memory/archive_service.py`](../../packages/memory/src/neobot_memory/archive_service.py) | 对用户/群/关键词的长期记忆条目，AI 自动总结与精简 |
| 用户画像 | [`user_profiles.py`](../../app/src/neobot_app/user_profiles.py) + [UserProfileSkill](./技能系统Skills.md) | 用户备注、性格印象，支持头像图片分析 |
| 好感度 | favorability | 数值化的关系亲密度（-1000 ~ 1000） |
| 自适应提示词 | AdaptivePromptSkill | Agent 可自主维护的永久记忆文本 |

> **现状说明**：短期记忆没有独立的记忆服务。当前可用的只有表中的「消息队列」（进程内的当前上下文）
> 与「档案记忆 / 用户画像 / 好感度 / 自适应提示词」（落库的长期记忆）。
> `packages/memory/service.py` 的 `MemoryService`（`remember`/`recall`）、
> `reader.py` 的 `MemoryReader` 协议与 `contracts/ports/memory.py` 目前都没有调用方，
> 属于未接入的规划接口：应用启动时会构造一个 `MemoryService` 实例，但没有任何代码读写它。

## 触发式记忆

`agent.memory.trigger` 配置：

- `group_interval`（默认 500）：群聊每 N 条消息触发一次记忆处理；0 表示禁用
- `private_interval`（默认 200）：私聊每 N 条消息触发一次；0 表示禁用
- `prompt_snippet_chars`（默认 120）：总结提示词中每条消息的最大展示字符数，超出部分截断，
  模型用 `archive_crud__read_pending_messages` 按需读取全文；0 表示不截断
- `max_tool_rounds`（默认 20）：单次总结最多工具调用轮次，防止工具失败时反复重试烧 token
- `max_summary_seconds`（默认 300）：单次总结的总时长预算，超出即中止本轮并进入失败冷却。
  至少要能装下两轮完整调用（第一轮工具调用 + 第二轮收尾），否则思考模型会在收尾时被腰斩
- `model_call_timeout_seconds`（默认 0 = 自动）：单次模型调用的超时。自动模式跟随该总结模型自身的
  `settings.timeout_seconds` 再留 15 秒余量，让 HTTP 层先超时并返回可读错误，而不是在模型正常推理
  途中被外层掐断——思考模式或 `reasoning_effort = "max"` 的模型单次调用常超过 60 秒，
  用固定短超时会导致"超时 → 重发完整上下文重试"的死循环，既慢又费 token
  （超时请求不返回 usage，本地用量统计里看不到，但服务端已按实际生成计费）

触发后由记忆 Agent 总结对话，写入用户/群档案（必要时同步写入物品/事件关键词档案）。

### 写入方式（增量优先，控制 token）

- 全量档案（`user_profile` / `group_profile`）：只用 `patch_archive` 增量写入
  （`op=append/prepend/replace/delete`），只提交改动片段，**不需要先读全文，也不重写整条档案**；
  需要修改既有内容时先用 `read_archive(mode='outline')` 定位、再按 `offset` 分页读该片段后定点修改。
- 定长摘要（`user_summary` / `group_summary`）：这是唯一允许用 `save_archive` 整条重写的档案，
  且仅在内容确实需要变化时重写，硬上限见 `archive.max_chars` / `archive.group_profile_max_chars`。
- 待总结消息按序号注入（`[序号] 发送者: 文本`），超长消息只注入片段；模型需要全文时
  调用 `archive_crud__read_pending_messages(conversation_key, indices)` 按需读取。
- 一次总结中所有工具调用都失败时，计数器会保留待下次重试，避免消息丢失。
- 已经成功写入过档案、之后才**超时或耗尽时长预算**的情况按**部分成功**清账：档案是 append 语义，
  重跑会把同一批事实再写一遍，而重试本身还要重发完整上下文且大概率以同样方式再次中止，
  因此只留告警（`reason=model_call_timeout` / `budget_exhausted`）不重试。
  一次工具都没成功时才保留计数器进入冷却重试。
- 总结成功后只销账「本次已总结」的消息：总结期间新到的消息会保留到下一轮，不会随清零一起丢掉；
  失败写回在计数器锁内只合并冷却字段，不会覆盖并发追加的消息。
- 总结调用的 token 用量按 `agent:memory` 记入用量统计，可在「统计与计费」中查看。

## 档案记忆（Archive）

档案是 Bot 对某个实体的长期记忆条目。相关配置 `agent.memory.archive`：

- `allow_delete`（默认 false）：是否允许 `delete_archive` 删除档案；关闭时该工具**不会注入给模型**，即使被调用也会被拒绝
- `allowed_tables`：允许访问的档案表名列表（留空不限制）；限制后 `save_archive` / `patch_archive` / `read_archive` / `list_archive` / `archive_stats`（指定 `table_name` 时）/ `delete_archive` 都会校验表名（内部待总结消息表 `memory_counter` 不受限制）
- `auto_compact_chars`（默认 200）：**已废弃**——原意是「单条档案超过此字符数触发一次 AI 自动精简」，
  但从未接线；容量治理请用下面的 `max_total_chars`
- `max_chars`（默认 500）：个人记忆**渲染**进系统提示词的展示上限（超出由模型分页查阅）
- `group_profile_max_chars`（默认 1500）：群聊记忆**渲染**进系统提示词的展示上限（超出由模型分页查阅）
- `max_total_chars`（默认 10000）：单条档案的**存储硬上限**（字符）；`0` = 禁用
- `overflow_action`（默认 `summarize`）：超限动作，见下面的「档案容量治理」
- `overflow_summary_cooldown_seconds`（默认 600）：同一 `(表, key)` 两次自动压缩之间的最小间隔

> 注意：`max_chars` / `group_profile_max_chars` 只限制**渲染进提示词**的长度，
> 与存储上限 `max_total_chars` 是**两件独立的事**。写入请优先用 `patch_archive` 增量修改，避免整条重写。

### 档案容量治理（`max_total_chars`）

超长档案会占库/占备份、让 `read_archive(full)` 与 `list_archive` 返回巨大结果。上限收口在
**服务层 `ArchiveMemoryService.set()`**（`save_archive` / `patch_archive` 与其它写入路径统一生效）：

| 环节 | 行为 |
|---|---|
| 判定 | `len(new_value) > max_total_chars` 且该表不在豁免名单 |
| `overflow_action = summarize` | **先完整落库**（不丢信息）→ 再异步触发一次压缩 → 工具**立即返回**，返回体带 `over_limit=true` / `total_chars` / `compressing` / `hint` |
| `overflow_action = reject` | 不落库，返回明确错误 + 压缩指引（模型自行用 outline/offset 阅读后压缩重试） |
| 单飞 | 同一 `(表, key)` 同时只允许一个压缩任务（复用自动总结的单飞机制） |
| 冷却 | 冷却期内重复超限不重复触发；**压缩失败会清除冷却**，让「下次写入再试」成立（重试节奏交给既有失败退避） |
| 兜底 | AI 不可用 / 压缩失败 / 压缩后仍超限 → **保留原内容不截断** + WARNING + 「超标」标记，靠 `list_over_limit` 可观测 |
| 可观测 | 服务层提供 `list_over_limit(table_name=None)` / `count_over_limit()`；面板「档案」页直接展示超限数与超限清单 |

> ⚠️ **内部表 `memory_counter` 永久豁免**：它存的是「待总结消息 JSON」，`group_interval=500` 时天然
> 超过任何上限。对它 reject 会让计数写不进去、整条自动总结管线断掉；对它 summarize 会让压缩器
> 吃掉尚未总结的消息。**误伤它的表现是「档案自动总结整体失效」，比长度超限严重得多。**
>
> 面板侧的档案写入（PUT `/api/archives/item`）**不做上限拦截**——面板是运维兜底入口，
> 管理员必须能写入并看到超限提示，超限档案再由 `list_over_limit` 枚举出来。

### AI 档案压缩

AI 压缩 = 由总结 Agent 读全文后**整条重写**一条档案（保留事实、合并重复、只丢冗余），
**不是**确定性的尾部截断。它有**两个触发点**，共用同一把单飞锁 `overflow:{表}:{key}`，
因此同一 `(表, key)` 同时只会有一个压缩在跑。

| 触发点 | 入口 | 目标字符数 | 用量归类 | 快照来源 |
|---|---|---|---|---|
| 写超限自动 | 写入超限且 `overflow_action = summarize` 时后台调度 | 固定取 `archive.max_total_chars` | `conversation_kind = archive_overflow` | `reason = auto` |
| 面板手动 | 「档案」页「AI 压缩」按钮 | 本次输入（见下） | `conversation_kind = archive_manual` | `reason = manual` |
| 面板批量 | 「档案」页「批量压缩超限档案」 | 本次输入，全部条目统一 | `conversation_kind = archive_manual` | `reason = manual` |

**目标字符数**（仅手动 / 批量有）：

| 项 | 规则 |
|---|---|
| 语义 | **只对本次压缩生效**，**不会**改写全局配置 `archive.max_total_chars`（前端只用 localStorage 记住上次输入） |
| 下限 | `200`；低于此值必然丢关键事实 |
| 上限 | `archive.max_total_chars`（大于 0 时）；`max_total_chars = 0`（容量治理关闭）时取兜底 `100000`——手动压缩此时**仍可用**，但不会因此开启自动压缩 |
| no-op | 目标 ≥ 当前字数 → **不调用模型**（零 token），直接返回「当前 N 字已不大于目标 M 字，无需压缩」 |
| 400 | 目标 < 200 / 目标 > 上限 / 缺少 `target_chars` / 内部表（`memory_counter`）触发，均返回 400 明确文案 |
| 批量 | 一次最多 **20** 条（被截断的剩余条数在返回体 `truncated` 里说明），**逐条串行**，统一一个目标；字数已不大于目标的条目直接标 `skipped` |

**压缩必须基于全文**：注入压缩提示词的正文超过 **60000** 字符时只保留首尾、中间以省略标记替代；
此时提示词**要求模型先用 `read_archive(mode="outline")` 定位、再用 `offset` 分页读回中间段**
（每页 500 字符，负数 offset 从尾部读）后才允许写回；写完必须核对工具返回的 `total_chars`
是否 ≤ 目标，未达标不得声称完成。

**安全阀全部复用自动总结那一套**：单飞键 / 单次时长预算（`trigger.max_summary_seconds`）/
工具轮数上限（`trigger.max_tool_rounds`）/ 工具连续失败熔断（`MAX_TOOL_FAILURES = 3`）/
失败指数退避 / 用量统计。手动路径**跳过**失败冷却（用户显式要求），但仍受预算与熔断约束。

**失败兜底**：模型异常 / 超时 / 没产生有效写入 / 压缩后仍大于目标 → **恢复压缩前原文**
（走乐观锁写入，不触发容量治理，避免「回滚 → 再次超限 → 再压缩」的循环）+ 记失败退避，
绝不静默留下半成品；回复管线不受影响。

**可追溯（压缩前快照）**：每次压缩**开始前**把原文原样写入快照表 `archive_snapshots`。

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `table_name` / `key` | 档案定位（复合索引 `(table_name, key, created_at)`） |
| `value` | 压缩前原文 |
| `total_chars` | 压缩前字符数（与面板 `total_chars` 同口径） |
| `version` | 压缩前的乐观锁版本号 |
| `reason` | `auto`（写超限自动）/ `manual`（面板手动 / 批量） |
| `operator_ip` | 触发者请求 IP（自动压缩为 NULL） |
| `created_at` | 写入时间（另有单列索引） |

- **保留策略**：同一 `(table_name, key)` 只保留最近 **10** 份（按 `created_at` 淘汰最旧），
  全表另有 **2000** 份兜底上限，防止大量不同 key 无限累积
- **失败 / 未达标且原文已成功恢复时删除本次快照**（原文未变，留痕是冗余，避免挤占 10 份配额）；
  若回滚失败则保留快照，作为该内容的唯一副本供人工恢复
- 面板「压缩历史」**只读**：列出时间 / 前后字数 / 来源 / 操作者，可查看某份快照全文，
  **不提供「恢复到此快照」**；需要恢复时人工读取该行内容后走既有编辑接口写回
- 建表迁移 `0026_add_archive_snapshots.py`，访问层
  [storage/repositories/archive_snapshot.py](../../packages/storage/src/neobot_storage/repositories/archive_snapshot.py)

**面板任务状态是进程内的**：手动 / 批量任务状态保存在内存（FIFO 最多 **50** 条；已结束且超过
**30 分钟**的记录在下一次访问时清理；进程重启即清空）。面板把它当「最近一次操作结果」，
长期历史以快照表为准。

**字符数工具**：总结 Agent 挂两把字符数工具，两把都复用服务层统计（与面板同一真相源，不新写 SQL）。

| 工具 | 用途 | 关键语义 |
|---|---|---|
| `archive_stats` | 跨条目统计（只读） | 入参 `table_name`（可选）/ `over_limit_only`（默认 false）/ `limit`（默认 50、上限 200）；返回 `max_total_chars`、`tables[]`（每表条目数 / 最长字数 / 超限条目数；内部表照常列出并带 `internal=true`）、`items[]`（超限清单，或指定表时的该表条目，含各自 `total_chars`；**排除内部豁免表**）、顶层 `over_limit_count`（全量超限计数）、`count` 与 `total_chars`（**本次 `items[]` 的条数与字数合计**，受 `limit` 限制）以及 `hint`。**[WIP · 语义待补强]** 顶层 `total_chars` **不是**「某表 / 全库真实合计」，而是本次返回条目的合计（受默认 `limit=50` 约束）；要拿真·全库合计需给服务层加一处 `sum_chars()`（当前刻意不新写 SQL，见 `TODO/待办事项.md`「WIP 与后续计划」） |
| `list_archive` | 枚举 / 检索条目 | 每条只给**开头 500 字符**的 `preview` + `total_chars` + `preview_truncated`，**不再返回整条 `value`**；默认 **5** 条、上限 **20** 条；返回体带 `hint` 引导用 `read_archive` 的 `outline` + `offset` 分页续读 |

> 面板条目列表的预览仍是 **200** 字符，与 `list_archive` 的 500 字符**口径有意不同**：
> 面板是人在表格里扫读、点开即有全文详情；工具取 500 是为了与 `read_archive` 的一页对齐
> （预览 = 第 0 页，续读从 `offset=1` 开始），且 5 × 500 字能完整落在单条工具返回
> **4000** 字符的预算内，不会被截断成半截 JSON。不要强行统一两者。

档案按实体分为：

- **用户档案**（user_profile）：Bot 对某位用户的印象
- **群档案**（group_profile）：Bot 对某个群的印象
- **物品/事件关键词档案**（`agent.memory.item_archive`，默认表名 `item_archive`）：以关键词为键的独立数据表，记录对特定物品、事件、话题的长期信息；自动记忆总结系统会同步写入

## 用户头像的本地存储与刷新

Bot 会为**聊过天的用户**在本地存一份头像（QQ 头像接口的 640px 原图），供卡片与面板
直接取用，渲染时**不联网**。

- **存储位置**：`<数据目录>/avatars/<QQ号>.png`；路径、获取时间与失败次数记在用户资料表
  （`user_data`）里。头像与用户资料**同表**——「有资料行 = 认识该用户」，天然覆盖聊过天的人，
  也不会出现「有资料、没头像」的两处数据不一致。
- **惰性刷新**：唯一的触发点是「用户**再次出现在聊天流**」。没有头像就取；已有头像且距上次
  成功获取超过 7 天（`refresh_days`）就更新；未过期则**完全不联网、不写库**。没有定时全量扫描。
- **不阻塞消息处理**：消息路径只做一次过期判定，下载在后台任务里执行；同一用户同时只允许
  一个下载，全局并发上限 `max_concurrent`（默认 2），超限的这次触发直接丢弃（该用户下次
  出现时自然重试）。
- **失败不更新**：下载失败时保留旧头像与旧时间戳（宁可旧头像，不要空头像），只累加失败次数；
  失败后进入 `fail_cooldown_seconds`（默认 600 秒）冷却，冷却期内不重试。失败不会留下半截文件。
- **容量治理**：单张头像超过 `max_bytes`（默认 512 KiB）不落盘；长期未活跃（默认 90 天，
  `keep_days`）的用户头像会被清理（删除文件 + 清空字段）。清理随聊天流流量触发，最多每
  24 小时一次。
- **取数接口**（宿主服务 `avatar_store`）：`get_path(qq)`、`get_data_uri(qq)`（`data:image/png;base64,…`，
  未就绪返回 `None`，内部有 128 条进程内缓存）、`maybe_refresh(qq)`、`stats()`。
- 配置项见[配置参考](../05-配置参考.md)的 `[avatars]` 段。

## 好感度（Favorability）

- 每次档案总结时可变更好感度，单次上限 `max_change_per_summary`（默认 ±5）
- 范围 `min_value` ~ `max_value`（默认 -1000 ~ 1000）
- Agent 可通过 FavorabilitySkill 查询；好感度影响 Bot 的互动倾向（体现在提示词中）

## 自适应提示词（Adaptive Prompt）

- `agent.memory.adaptive_prompt_enabled`（默认 true）：Agent 可自主维护一段「永久记忆」文本
- `adaptive_prompt_max_chars`（默认 200）：超出自动截断
- 实现：`AdaptivePromptSkill`，Agent 通过工具读写，内容每次注入系统提示词

## 档案获取窗口

`chat.archive_fetch_window`（默认 20）：群成员列表窗口，只列出消息队列中最新的 N 条消息的发送者。

## 提示词中的档案注入

- **群聊**：默认只注入群档案（`group_summary` 优先、缺失时 `group_profile`，超长截断+引导）。
  群员档案默认**不注入**（`chat.inject_member_archives=false`），成员列表只保留昵称/QQ/好感度/印象等轻量信息，
  并附上按需读取引导：agent 需要某位群友的记忆时用
  `archive_crud__read_archive`（`user_summary` 优先、`user_profile` 回退，key=QQ号）按需读取。
  设为 `true` 可恢复旧行为（注入窗口内群员的个人档案）。
- **私聊**：注入对方的个人档案，超长时截取开头部分（`archive.max_chars`）并附分页/大纲按需读取引导。
