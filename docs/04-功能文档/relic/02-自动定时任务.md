# 自动定时任务

> 模块 R-B · 归属 relic 插件 · 状态：设计稿（未实现）

对白名单私聊用户，Bot 会观察聊天内容，分析「他/她什么时候可能需要被关心」，
并把结论落成本体的定时任务——到点由 Bot 自己组织一句问候。

例：用户说「五点去吃晚饭」→ Bot 建 17:30 的任务问「晚饭怎么样」；
用户说心情不好 → Bot 在第二天早上问「今天感觉好点了吗」。

## 1. 目标与非目标

**目标**

1. 只对白名单用户生效，绝不全量分析。
2. 触发条件可预期：攒够 30 条立即分析，否则每小时最多一次。
3. 产出是**少量、不打扰**的定时任务（默认每人同时最多 3 个待触发）。

**非目标**

- 不做实时插话，不干预正在进行的回复管线。
- 不新建调度设施：任务创建直接用本体 `scheduled_task_manager`。

## 2. 白名单

这张表**属于精益求精体系**（R-C 及其自动开启的陪伴分析 R-B），月度规划的节日任务不使用它。

写入只有两个入口，二者都要求**私聊场景**：

| 入口 | 名称 | 说明 |
|---|---|---|
| agent 工具 | `relic__enable_companion` | 用户在私聊里**明确要求**「以后多关心我」时调用；工具内部再校验一次会话类型 |
| 管理员命令 | `/relic on <QQ> [companion\|perfection]` | `permission=1`（次级管理员以上） |

删除：`relic__disable_companion`、`/relic off <QQ>`。

> 功能开关 `companion=true` 只是允许这套机制工作；**没有白名单用户时不会产生任何模型调用**。
> 只想要「被关心」而不想要深度分析的用户，行里 `companion=1`、`perfection=0`。

## 3. 计数与触发

消息计数：插件注册 `@plugin.message()`（空 pattern 匹配全部消息，`packages/modloader/src/neobot_modloader/command_dsl.py:97-98`），
只处理「私聊 + 白名单用户 + 非命令消息」，非阻塞地累加 `relic_message_counter.pending`。

调度循环每 `companion_interval_minutes`（默认 60）检查一次：

```text
对每个白名单用户：
  if pending >= companion_message_threshold(30): 立即分析
  elif pending > 0 and 距上次分析 >= interval: 分析
  else: 跳过
```

达到 30 条不等时间窗，是为了让「刚聊完一大段」尽快得到回应；不足 30 条则每小时最多一次，避免碎消息反复触发。

## 4. 分析（多轮工具调用）

一次分析 = 一个带工具的 `neobot_chat.Agent`（`relic_analyst` 路由）。**结果只认工具调用**，assistant 正文直接丢弃。

输入不预塞进提示词，由 agent 自己按需读取：

| 工具 | 来源 | 用途 |
|---|---|---|
| `relic__search_messages` | R-D | 读该用户最近消息（可跨会话） |
| `relic__list_diary_materials` / `relic__read_diary_material` | R-D | 他的近期素材 |
| `relation__list_relations` | M-A | 关系网 |
| `archive_crud__read_archive` | 本体 | 用户档案 |
| `submit_companion_tasks` | relic | **提交要建的定时任务** |
| `no_action` | relic | 明确「本轮不需要关心」 |

`submit_companion_tasks` 参数：

| 参数 | 类型 | 约束 |
|---|---|---|
| `tasks` | array | 每项 `{when, reason, prompt}`；`when` 为本地 ISO8601 |
| `reason` | string | 整轮判断依据，写分析日志 |

`no_action` 参数：`reason`。两个提交工具二选一，必须调用其中一个。

落地规则（在工具内校验，不合格返回错误让模型改，不重复建）：

1. `when` 必须在未来 10 分钟内到 7 天内；落在安静时段（`quiet_hours`，默认 23:30–08:00）的任务顺延到 08:30。
2. 与已有待触发任务按「同一天 + 相似主题」去重。
3. 该用户待触发任务数 ≥ `max_pending_tasks`（默认 3）→ 丢弃并记 debug。
4. 通过后经 `scheduled_task_manager.create_task` 建 `once` 任务，`bindings=[ConversationRef("private", user_id)]`。

预算：`analysis_max_iterations`（默认 1000，兜底）、`analysis_timeout_seconds`（默认 120）。
轮次不是成本控制手段，真正的刹车是超时、`max_pending_tasks` 与白名单。
完成后：`pending=0`、写 `relic_analysis_log`（含 `task_count` 与 `reason`）、按 `agent:relic` 记账。

## 5. 接口

| 类型 | 名称 | 说明 |
|---|---|---|
| 路由 | `agent_model.relic_analyst` | 分析模型编号（默认 3） |
| 工具 | `relic__enable_companion` / `relic__disable_companion` | 当前用户开关 |
| 命令 | `/relic on\|off <QQ>`、`/relic list` | 管理员 |
| 能力 | `relic.status` | 返回白名单数量、今日分析次数，供面板/其它插件 |

## 6. 配置

| 键 | 默认 | 说明 |
|---|---|---|
| `companion` | true | 功能总开关 |
| `companion_interval_minutes` | 60 | 检查间隔 |
| `companion_message_threshold` | 30 | 立即分析的条数阈值 |
| `max_pending_tasks` | 3 | 每用户待触发任务上限 |
| `quiet_hours` | "23:30-08:00" | 不排任务的时段 |
| `analysis_history_limit` | 50 | 送入模型的消息条数上限 |
| `analysis_max_iterations` | 1000 | 分析 agent 最大工具轮数（兜底） |
| `analysis_timeout_seconds` | 120 | 分析 agent 总超时 |

## 7. 失败与边界

- 未调用 `submit_companion_tasks` / `no_action`（超时或撞到 1000 轮兜底）→ 本次丢弃，保留 `pending`，下轮再试。
- 工具返回校验错误（时间越界、任务超上限）→ 模型可改后重提，不改也按丢弃处理。
- 单用户异常不影响其它用户（循环内 try/except + 每用户日志）。
- 连续失败 3 次 → 当天跳过该用户，写 warn。
- 定时任务管理器不可用 → 停用本模块并写 warn（不静默失败）。
- 插件停用/卸载：`ctx.create_task` 托管的循环被取消；已建的定时任务保留（用户可见、可手动删）。
- 不做「任务到期后回收失败」的重试——定时任务派发失败由本体自己的重试机制负责。

## 8. 测试与验收

- 单元：阈值分支（28 条不触发、30 条触发）、时间分支（不足 30 条但满 1 小时触发）。
- 单元：`when` 越界、安静时段顺延、`max_pending_tasks` 丢弃、去重。
- 单元：白名单外用户不计消息、不分析。
- 手工：给自己开白名单，聊 30 条，观察下游任务创建与提醒质量。
