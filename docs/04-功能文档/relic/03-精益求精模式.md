# 精益求精模式

> 模块 R-C · 归属 relic 插件 · 状态：设计稿（未实现）

「精益求精」是私聊限定的深度观察模式：每天晚上 00:00 起排队，逐个对重点用户做一次带工具的深度分析，
结论写进该用户的档案之后，让后续每次对话都自然带上一段「近期状态」。

开启即自动开启 [自动定时任务](./02-自动定时任务.md)——两者共用同一行白名单的两个布尔列。

## 1. 目标与非目标

**目标**

1. 对重点用户每天一次、可解释的长期观察，结论落档案。
2. 多用户时串行排队，固定间隔，避免同时打满模型。
3. 分析过程可追溯：读了哪些来源、花了多少 token，都进日志。

**非目标**

- 不替代本体记忆 agent（档案总结仍由本体负责）。
- 不实时介入聊天，不产生用户可见消息。

## 2. 开启方式

| 入口 | 名称 | 说明 |
|---|---|---|
| 管理员命令 | `/relic on <QQ> perfection` | `permission=1` |
| agent 工具 | `relic__enable_perfection` | 用户在私聊里明确要求「深度了解我」时；工具内部校验私聊 + 二次确认 |

开启 `perfection` 时同时把 `companion` 置真（需求：该功能会自动开启自动定时任务）。

## 3. 午夜队列

```text
每天到 perfection_start_hour（默认 0 点）：
  收集全部 perfection=1 的用户
  按 last_analyzed_at 升序（最久没分析的先）
  for 每个用户:
      跑一次分析（可能耗时 1–3 分钟）
      await sleep(perfection_dispatch_interval_seconds)   # 默认 300
  记录 run_id 与总用时
```

间隔固定 5 分钟的意义是控制并发：一次分析是带工具的多次模型调用，同时跑 N 个会挤占主对话的模型额度。

跨天处理：若队列未跑完就跨过第二天，剩余用户顺延到当天继续，不叠加新队列。
进程重启：队列不持久化，重启后从「今天尚未分析」的用户重新开始（`relic_analysis_log` 判重）。

## 4. 分析过程

一次分析 = 一个带工具的 `neobot_chat.Agent`（`relic_analyst` 路由），system prompt 要求：

1. 先读该用户档案（`user_profile` / `user_summary`），了解已有结论，避免重复。
2. 用工具查证据，不要凭印象下结论。
3. 用 `submit_analysis` 提交一段 ≤ `max_analysis_chars`（默认 800 字）的结论，包含：观察到的心理需求、证据、建议的相处方式；没有证据就调 `skip_analysis`。

可用工具：

| 工具 | 来源 | 用途 |
|---|---|---|
| `relic__search_messages` | R-D | 按用户跨会话检索消息（含其他群聊） |
| `relic__list_diary_materials` / `relic__read_diary_material` | R-D | 读日记素材的 summary 与来源 |
| `relation__list_relations` | M-A | 查该用户的关系网 |
| `group_management__search_groups` | M-B | 查他/她所在的群是什么性质 |
| `archive_crud__read_archive` | 本体 | 读现有用户档案，避免重复结论 |
| `submit_analysis` | relic | **提交结论正文**（`text`，≤ `max_analysis_chars`） |
| `skip_analysis` | relic | 证据不足时明确放弃（`reason`） |

**结论只认 `submit_analysis` 的工具参数**，assistant 正文不落库；`skip_analysis` 与 `submit_analysis` 必须调用其一。

预算：`max_iterations`（默认 1000，兜底，正常不会撞上）、`timeout_seconds`（默认 180）。超时或未提交 → 本次放弃并记日志。

## 5. 结论落点

写 `relic_user_analysis`：`user_id`、`text`、`updated_at`，保留最近 3 条（旧的覆盖）。

注入方式（本体唯一改动点）：`app/src/neobot_app/user_profiles.py:384-417` 的 `_fetch_user_archive`
在返回档案正文后追加一段：

```text
[近期状态]
<最新一条结论>
```

约束：
- 只读追加，不改写档案本体；档案与结论分别有字数上限，超限截断。
- 结论为空或插件未启用时不追加。
- 注入内容与档案一样受敏感字段规则约束（不写凭据）。

## 6. 配置

| 键 | 默认 | 说明 |
|---|---|---|
| `perfection` | true | 功能总开关 |
| `perfection_start_hour` | 0 | 每天几点开始排队 |
| `perfection_dispatch_interval_seconds` | 300 | 每个用户之间的间隔 |
| `max_iterations` | 1000 | 单次分析的工具轮数（兜底） |
| `timeout_seconds` | 180 | 单次分析总超时 |
| `max_analysis_chars` | 800 | 结论字数上限 |
| `perfection_daily_limit` | 1 | 每用户每天最多分析几次 |

## 7. 失败与边界

- 单用户失败：记 `relic_analysis_log.status=error`，跳过该用户继续下一个，不重试（第二天再来）。
- 超时：中断工具循环，保留已收集内容也不写（避免半成品结论进档案）。
- 队列中断（插件重载/进程退出）：不补跑，当天剩余用户下一轮继续。
- 结论质量：没有证据时模型应调 `skip_analysis`；未调用任何提交工具的一律不落库。
- 成本：`perfection_daily_limit` + 队列串行 + 每用户单次预算，三个上限叠加。

## 8. 测试与验收

- 单元：队列排序（最久优先）、间隔调用（假时钟）、跨天顺延。
- 单元：`max_iterations` 超限、`timeout_seconds` 超时、`submit_analysis` 参数超限被拒、`skip_analysis` 不落库。
- 集成：`_fetch_user_archive` 在有/无 `relic_user_analysis` 时的输出差异。
- 手工：给自己开 perfection，把 `start_hour` 调到当前时间 +1 分钟，观察队列与结论注入。
